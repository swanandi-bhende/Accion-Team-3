# How to Verify Independently

This guide explains how external reviewers (such as industry evaluators) can independently verify the proofs generated by the Verifiable AI Execution Subsystem without needing TEE hardware or deploying the entire system.

The subsystem exposes a Verification Interface over a REST API that lets anyone verify a proof.

## Starting the Verification Server
To start the verification server locally:

```bash
uvicorn verification.app:app --port 8000
```
*(Note: If you're running the full docker-compose stack, this service is exposed automatically.)*

## Verifying a Valid Proof

Here is a copy-pasteable example of a successful verification request. The proof format in this example is `tee_attestation`.

```bash
curl -X POST http://localhost:8000/verify \
  -H "Content-Type: application/json" \
  -d '{
    "proof_format": "tee_attestation",
    "public_inputs": {
      "input_hash": "e3b0c44298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855",
      "output_hash": "e3b0c44298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855"
    },
    "proof_reference": "QmTestExample123"
  }'
```

### Expected Response

A successful verification yields a `result: true` and mirrors the `public_inputs` (with no reason code):

```json
{
  "result": true,
  "timestamp": 1729452000.0,
  "public_inputs": {
    "input_hash": "e3b0c44298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855",
    "output_hash": "e3b0c44298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855"
  }
}
```

## Verifying a Tampered Proof

To see the system catch a tampered proof, change the `output_hash` in the `public_inputs` so it no longer matches what the enclave signed:

```bash
curl -X POST http://localhost:8000/verify \
  -H "Content-Type: application/json" \
  -d '{
    "proof_format": "tee_attestation",
    "public_inputs": {
      "input_hash": "e3b0c44298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855",
      "output_hash": "malicious_fake_hash_value"
    },
    "proof_reference": "QmTestExample123"
  }'
```

### Expected Response

The system will reject it with `result: false` and provide a specific `reason_code` (`proof_mismatch` in this case):

```json
{
  "result": false,
  "timestamp": 1729452010.0,
  "reason_code": "proof_mismatch"
}
```

## Reason Codes

If verification fails, you will receive one of the following reason codes:
- **`proof_mismatch`**: The signature is valid, but the hashes inside the proof do not match the public inputs you provided (e.g. someone tampered with the inputs/outputs).
- **`invalid_signature`**: The hardware signature doesn't match the enclave's public key (e.g. the proof was generated by an untrusted party).
- **`expired_attestation`**: The proof is too old based on the configured attestation expiry limit.
- **`malformed_proof`**: The proof bytes cannot be parsed or resolved.
